## Tamaño del conjunto residente

Con menos frames por proceso caben **más procesos** en RAM, así que hay más probabilidad de tener alguno listo. Pero si un proceso tiene **muy pocos** frames, la tasa de fallos se dispara. Pasado cierto punto, darle **más** frames casi no mejora nada, por la localidad.

<MemVirtualFig fig="marcosfallos">
**Cómo leerlo:** a la izquierda, con muy pocos marcos, el proceso no alcanza a tener su zona de trabajo y falla todo el tiempo. Cuando los marcos cubren su working set, la curva se aplana: dar más ya casi no baja los fallos. Por eso conviene darle a cada proceso **lo justo para su working set** y usar el resto para otros.
</MemVirtualFig>


| Asignación | Idea | Problema |
| --- | --- | --- |
| **Fija** | número fijo de frames por proceso, decidido al crearlo (según el tipo de proceso o lo que pida) | si es poco hay muchos fallos; si es mucho, caben pocos procesos |
| **Variable** | el número de frames cambia durante la vida del proceso | hay que **medir** el comportamiento: overhead del SO |

## Alcance del reemplazo: local o global

<EnSimple titulo="En simple: ¿le quito a quién pidió o a cualquiera?">
Tu escritorio está lleno y necesitas un libro más.
- **Local:** devuelves uno **de tu propio** escritorio. Tu espacio no cambia.
- **Global:** devuelves uno de **cualquier** escritorio, incluso el de un compañero. Tú creces y él se achica.

Global es más simple y flexible, pero puede perjudicar a un compañero que necesitaba ese libro.
</EnSimple>


- **Local:** la víctima sale del **mismo proceso** que causó el fallo.
- **Global:** la víctima puede ser **cualquier** página no bloqueada de la memoria.

<MemVirtualFig fig="localglobal">
**Cómo leerlo:** arriba, la RAM antes del fallo (3 marcos de A, 5 de B); abajo, después. Con reemplazo local, A se reemplaza a sí mismo y los tamaños no cambian. Con global, A le quita un marco a B: A crece y B se achica. Ejemplo propio.
</MemVirtualFig>


| | **Reemplazo local** | **Reemplazo global** |
| --- | --- | --- |
| **Asignación fija** | el número de frames no cambia y la víctima sale de las páginas del propio proceso | **imposible**: si se le quita una página a otro, el tamaño ya no sería fijo |
| **Asignación variable** | se reevalúa cada cierto tiempo cuántos frames darle; la víctima sale de los propios | **la más fácil y la más usada** (por ejemplo, en muchos UNIX): el proceso que falla **crece**, otro pierde un frame |

**Variable + global** es simple, pero no tiene forma de saber **a quién** le conviene quitarle un frame: puede quitárselo a un proceso que lo necesitaba. Se compensa con *page buffering*: la página quitada queda un tiempo en una lista y se recupera barato.

**Variable + local** necesita una estrategia para decidir **cuántos** frames dar. Ahí entra el working set.

<Predice titulo="Debate: elige y defiende" pregunta="En la misma máquina corren un reproductor de audio (pocas páginas, siempre las mismas, no puede cortarse) y una compilación enorme que no para de pedir memoria. ¿Usarías reemplazo <strong>local</strong> o <strong>global</strong>? ¿Qué cambia si solo corre la compilación?">

- **Con los dos procesos:** **local** (con asignación variable), porque con reemplazo global la compilación, que falla mucho, le iría quitando frames al reproductor hasta cortarlo. Local **aísla** a los procesos: los fallos de uno no castigan a otro.
- **Solo la compilación:** **global** es más simple y aprovecha toda la RAM libre sin tener que medir el working set. Por eso es la opción más usada en los UNIX.
- **Criterio:** global maximiza el uso de la memoria; local da previsibilidad. Ninguno gana siempre.

</Predice>

## Working set

<EnSimple titulo="En simple: lo que tienes sobre la mesa">
El **working set** son las páginas que el proceso usó en **los últimos Δ accesos**: lo que tiene «sobre la mesa» ahora.

**Ejemplo trivial:** referencias **A B A C D**.
- Con **Δ = 2** (los 2 últimos accesos: C D) → `W = {C, D}`.
- Con **Δ = 4** (los 4 últimos: B A C D) → `W = {A, B, C, D}`.

La regla: un proceso solo se ejecuta si su working set **cabe completo** en la RAM. Si no cabe, va a pasar el tiempo trayendo páginas.
</EnSimple>


**Definición** (Denning): $W(t, \Delta)$ es el conjunto de páginas referenciadas en las **últimas Δ referencias** (unidades de tiempo virtual), mirando hacia atrás desde el instante t.

**Propiedades:**
- $W(t, \Delta + 1) \supseteq W(t, \Delta)$: una ventana más grande nunca tiene menos páginas.
- $1 \le |W(t,\Delta)| \le \min(\Delta, N)$, donde N es el número de páginas del proceso.
- Su tamaño **sube** durante las transiciones entre fases de localidad (las páginas viejas siguen en la ventana mientras llegan las nuevas) y **baja** cuando el proceso se estabiliza.

**La estrategia del working set:**
1. Monitorea el working set de cada proceso.
2. Quítale periódicamente las páginas que **salieron** del working set (reemplazo tipo LRU).
3. Un proceso solo se ejecuta si su working set **cabe completo** en RAM.

**Problemas prácticos:** el pasado no siempre predice el futuro, porque cambia la localidad; medir el working set **exacto** es caro (habría que registrar cada referencia), y el **Δ óptimo** es desconocido y varía. Por eso se usan aproximaciones.

### Aproximaciones: PFF y VSWS

- **PFF** (*Page Fault Frequency*): cada página tiene un bit de uso. En cada fallo, el SO mira el tiempo virtual desde el fallo anterior:
  - si es **menor que un umbral F** (fallos muy seguidos), agrega la página al conjunto residente: el proceso **crece**;
  - si no, **descarta** todas las páginas con bit de uso 0 y pone los demás bits en 0: el proceso **se encoge**.

  El punto débil: durante una **transición de localidad**, las páginas viejas no alcanzan a salir y el conjunto residente se infla.
- **VSWS** (*Variable-Interval Sampled Working Set*): evalúa el working set en instantes de muestreo con tres parámetros:
  - **M**: intervalo mínimo;
  - **L**: intervalo máximo;
  - **Q**: número de fallos permitidos entre muestras.

  El intervalo termina al llegar a L, o al llegar a Q fallos si ya pasó M. Así reacciona rápido en las transiciones sin muestrear de más en las fases estables.

## Política de limpieza

<EnSimple titulo="En simple: lavar los platos">
Las páginas modificadas son **platos sucios**: antes de reutilizarlos hay que lavarlos (escribirlos al disco).
- **Por demanda:** lavas el plato **justo cuando lo necesitas**. El que espera la comida espera también el lavado (dos E/S).
- **Precleaning:** lavas **todo de antemano**, en tandas. Pero quizá ensucies otra vez un plato que ya lavaste (E/S desperdiciada).

El punto medio es el **page buffering**: lavar en tandas solo lo que ya está apartado para salir.
</EnSimple>


¿**Cuándo** se escribe al disco una página **modificada**?

| Política | Cuándo | Problema |
| --- | --- | --- |
| **Por demanda** | solo cuando la página es elegida como víctima | el proceso que falló espera **dos** E/S: escribir la víctima y leer la nueva |
| **Precleaning** | antes de que haga falta, en lotes | se escriben páginas que quizá se vuelvan a modificar antes de ser expulsadas: E/S desperdiciada |

**Mejor solución: page buffering.** Las páginas reemplazadas van a dos listas, **modificadas** y **no modificadas**. Las modificadas se escriben **en lotes** y pasan a la lista de no modificadas. De ahí se pueden **recuperar** si se vuelven a referenciar, o se **reutilizan** sus frames si se pierden.

<MemVirtualFig fig="buffering">
Es el mismo esquema de [page buffering](/final/memoria-virtual/reemplazo/#page-buffering), visto desde la limpieza: las páginas sucias se escriben **en lote** (arriba a la derecha) y recién después se reutiliza su frame.
</MemVirtualFig>


## Control de carga y thrashing

<EnSimple titulo="En simple: demasiada gente en la cocina">
Con **pocos cocineros**, la cocina está ociosa. Al agregar más, se produce más… hasta que son **tantos** que no caben, se estorban y pasan el tiempo pidiéndose los utensilios. La producción **se desploma**.

Eso es el **thrashing**: demasiados procesos, cada uno con muy pocos marcos, y la CPU casi solo espera al disco. La solución es **sacar a algunos** (suspender procesos) hasta que los demás tengan espacio suficiente.
</EnSimple>


El **nivel de multiprogramación** es el número de procesos residentes en RAM.

- **Muy pocos:** a menudo todos están bloqueados, así que la CPU queda ociosa.
- **Demasiados:** cada uno tiene un conjunto residente insuficiente y la tasa de fallos se dispara. Es el **thrashing**, que Stallings muestra en la fig. 8.21:
  - el uso del procesador **sube** al agregar procesos,
  - llega a un **máximo**,
  - y **cae en picada**: la CPU pasa el tiempo esperando al disco de paginación.

<MemVirtualFig fig="thrashing">
**Cómo leerlo:** al agregar procesos, la CPU se ocupa más porque casi siempre hay alguno listo. Pasado el máximo, cada proceso tiene muy pocos marcos y vive fallando (zona roja): la CPU se queda esperando al disco. La solución no es agregar procesos sino **sacar** algunos, para volver a la izquierda del máximo.
</MemVirtualFig>


**Criterios para elegir el nivel:**
- **Working set:** solo se ejecuta un proceso si su working set está residente. Eso regula la carga de forma implícita.
- **Criterio L = S** (Denning): ajustar la carga para que el **tiempo medio entre fallos (L)** sea igual al **tiempo medio de atender un fallo (S)**. Así se maximiza el uso del procesador.
- **Criterio del 50 %:** mantener la **utilización del dispositivo de paginación** cerca del 50 %.
- **Adaptar Clock:** si el puntero da vueltas **muy rápido**, hay escasez de memoria; si gira **lento**, sobra memoria y caben más procesos.

**Si hay que bajar la carga, ¿qué proceso se suspende** (se pasa a disco)? Stallings da seis candidatos:

| Candidato | Razón |
| --- | --- |
| el de **menor prioridad** | política de planificación |
| el que **más fallos** está causando | probablemente no tiene su working set residente; suspenderlo libera un dispositivo saturado |
| el **último activado** | es el que menos probablemente tiene su working set completo |
| el de **conjunto residente más pequeño** | cuesta poco volverlo a cargar después, aunque perjudica a los procesos de localidad pequeña |
| el **más grande** | libera más frames de una vez |
| el que tiene **más tiempo de ejecución restante** | aproxima la política de menor tiempo restante |

<Detective titulo="pregunta típica de análisis" sintoma="La CPU está al <strong>10 %</strong> y el disco de paginación al <strong>98 %</strong>. El administrador agrega más procesos para «aprovechar la CPU ociosa» y todo empeora. ¿Qué pasa y qué harías?" pista="Mira la fig. 8.21: ¿qué le pasa al uso de la CPU cuando el nivel de multiprogramación pasa del máximo?">

Es **thrashing**. Hay demasiados procesos para la RAM disponible: ninguno tiene su working set residente, así que todos generan fallos continuamente y esperan al disco. Agregar procesos (para «aprovechar la CPU ociosa») lo **empeora**.

**Qué hacer:**
- **bajar el nivel de multiprogramación**, suspendiendo procesos con alguno de los criterios de la tabla;
- agregar RAM;
- o asignar frames según el working set o PFF, para que cada proceso activo tenga lo que necesita.

Lo que **no** sirve: un disco de paginación un poco más rápido o una CPU más rápida. El cuello de botella es la falta de frames.

</Detective>
